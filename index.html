LLM choice

Words on these pages

Definitions

Short meanings for the words the other tabs keep using.

LLM
A large language model. A program that finishes text. You give it a start, and it keeps guessing the next piece.
Token
A chunk of text, usually a word or a piece of a word. The model reads and writes tokens, not single letters.
Vocabulary
The fixed list of tokens the model is allowed to write. A guess gives every token in that list a chance.
Vector
A list of numbers standing for one token. Tokens that show up in similar sentences get similar lists.
Embedding
The vector for one token. It is learned during training. It is not a number someone typed in by hand.
Transformer
The 2017 design almost every current LLM uses. A stack of layers, and each layer uses attention.
Pre-training
The long first pass. The weights start random. The only job is to predict the next token on a huge cleaned pile of text.
Post-training
Later passes that teach the model to answer like an assistant. Instruction tuning is one. A preference pass, which keeps the better of two replies, is another.
Backpropagation
The walk that computes the gradient for every weight, so the downhill step knows which way to nudge each number.
Batch
Several requests on the same GPU at once. The chip does their multiplications together, instead of waiting for one reply to finish before starting the next.
Attention
The model looking across the other words in the sentence to decide what the current word means. “Bank” leans on “river” or on “money.”
Layer
One pass of looking and mixing. A large model stacks dozens of layers. The last layer produces a score for every possible next token.
Score
A raw number for one possible next token. Scores can be any size. They are not chances yet.
Chance
A score after it has been turned into a share between 0 and 1. All the chances for the next token add up to 1.
Softmax
The formula that turns scores into chances. It boosts the big scores and shrinks the small ones.
Context
The stretch of text the model can see at once. It cannot see past that stretch.
Loss
How surprised the model was by the real next token. The loss is small when it gave that token a high chance, and large when it almost ignored it.
Gradient
The slope of the loss. It says which way each stored number should move so the next guess is less surprised.
Training
Showing the model real text, scoring each guess with the loss, and nudging the stored numbers a little. This happens many times. The loss never has to reach zero.
Instruction tuning
A later training pass, on examples of the reply a person wanted. The first pass teaches what usually comes next. This pass teaches the model to answer the request.
Fine-tuning
More training, starting from weights that already exist, on your own examples. The weights move, and you get a new file. Answering does not do this. The weights stay put while the model replies.
LoRA
A way to fine-tune by training a small set of extra numbers, while the original weights stay frozen. It uses far less memory than rewriting every weight.
Weight
One of the stored numbers inside the model. The weights stay put while the model answers. A new sentence is multiplied by them, and that multiplication produces the chances. They are not the list of possible next tokens.
Open model
A file of weights you are allowed to copy and run. The practice text is not the model. The weights are. Most of these are open weights, not fully open source.
Frontier
Among the most capable models available at the moment. The word says nothing about whether you can download the file. A frontier model is often closed, and a few open-weight models sit near that front too.
Open weights
The weight file is published. You can run it on a GPU you rent or own. The training text and the full training recipe usually stay private.
Open source
Weights, training code, and enough of the data to rebuild the model, under a license that allows that. This is rarer than a published weight file.
Closed model
The weights stay at the lab. You send a prompt to their API and get tokens back. You never receive the file.
CPU
The ordinary processor in a computer. It is built for one job at a time: open a file, branch, decide.
Chip
The calculator on a GPU board. One board has one chip. The chip does the multiplications.
VRAM
The memory on one GPU board. It is several small memory chips added together. The weights sit here while the chip works.
GPU
One board: one chip plus that board’s VRAM. Counting GPUs means counting boards. The chip on one board cannot use the memory on another board.
Byte
A small unit of memory. At half precision, one weight takes 2 bytes. A billion weights is about 2 GB.
Bit
A smaller step than a byte. One byte is 8 bits. At 4 bits, one weight takes about half a byte, so the file is about a quarter of the half-precision size.
Half precision
Storing each weight in 16 bits, which is 2 bytes. This is the usual size before quantization. A billion weights is then about 2 GB.
Gigabyte
About a billion bytes, written GB. The memory formulas on these pages are in gigabytes.
Data centre
A room of GPU boards, with power, cooling, and fast cables between the boards. A frontier-size model is split across many boards there.
API
A way to send your text to a company’s computers and get a reply back. Their machines hold the weights. They can store what you sent.
Prompt
The text you give the model before it starts guessing. On an API, the prompt leaves your machine. On a GPU you own, it stays there.
Self-hosting
Running a published weight file on a computer you control. The prompt is multiplied there. You can also keep training that file on your own examples. A lab API is not self-hosting, even when the lab serves an open file.
Runner
The program that loads the weights into VRAM and writes the next token. Your own software sends the prompt to the runner and reads the reply.
Quantization
Storing each weight with fewer bits so the file uses less VRAM. At 4 bits the file is about a quarter of the half-precision size. The answers get a little less exact.
KV cache
Extra memory used while answering, so the model can look back at the prompt and the tokens it has already written. It grows with the length of the conversation, and with how many conversations run at once. The weights do not grow.
License
The rules that come with the weight file. They say who may run it, and for what. A published file is not a promise that every use is allowed.
Rent
Paying to use someone else’s GPU for a while. You run the open file. They own the machine, so they can see it and switch it off.
Practice text
Sentences used to train a model, or later to try a copy. The practice text is not the model. The weights are. A first self-hosted check uses stand-in sentences that are not private.
Zero data retention
A promise that a company does not keep the prompt and the reply after the answer is sent. A request their safety systems flag can still be kept. Every company in the path has to make the promise, or the prompt still sits with the one that did not.
Distillation
Training a new model on another model’s replies, so the new file imitates it. Anthropic’s usage policy requires their permission before Claude’s outputs are used this way.
Independent variable
The thing you change on purpose between runs. If two things change at once, you cannot tell which one moved the score.
Dependent variable
The thing you measure after the run: the score, the seconds, the dollars.
Constant
What you keep the same so the independent variable is the only difference.
Pass at one
The first try is the one that counts. The task passes only if that try meets the test. Written pass@1.

From nothing

How an LLM works

If you have never heard the term: an LLM is a large language model. It is a program that finishes text. You give it a start. It guesses the next piece, sticks that piece on, and guesses again.

It does not look answers up.

A dictionary stores meanings. An LLM does not. It has practiced on a huge pile of text, and what remains is a giant list of numbers. Those numbers are good at guessing what piece of text usually comes next.

The pile is collected first: books, web pages, code, articles, and the rest. Then it is cleaned. Duplicates go. So does broken or low-quality text. What remains is practice text, not the model.

The rest of this page is that idea, slowly. Words become pieces. Pieces become numbers. Numbers get adjusted until the guesses are less wrong.

Text is chopped into tokens.

A token is usually a word, a piece of a word, or a mark like a comma. The model never sees “unbelievable” as letters. It sees a few chunks, and each chunk has an ID number.

untoken 1 believtoken 2 abletoken 3

The ID is just a label, like a locker number. The meaning lives in the list of numbers that comes next, not in the ID itself.

Each token becomes a list of numbers.

That list is called a vector, and for a token it is also called an embedding. A real model uses thousands of numbers per token. Four is enough to see the idea. The list is learned. Tokens that show up in similar places get similar lists. “Cat” sits nearer “dog” than “invoice”.

It looks at the other words to decide.

The word “bank” is ambiguous. The model looks across the sentence and leans on the words that matter. This look is called attention. In 2017 attention became the whole design, called a transformer, because looking at every word at once trains well on GPUs. A usual picture is the word “it” in “the programmer fixed the server because it crashed,” leaning back on “server.” That lean is learned. It is not a rule someone wrote.

It does that look many times.

One look is not the model. The list goes through a stack of layers. Each layer looks again and mixes the numbers. A large model has dozens of layers. The last layer does not output a sentence. It outputs a score for every token that could come next.

Scores become chances that add up to 1.

A score can be any number. A chance has to sit between 0 and 1, and the chances have to add up to 1. The formula that does this is called softmax. It boosts the big scores and shrinks the small ones.

chanceᵢ = escoreᵢ / (escore₁ + escore₂ + …)

A reply is one token at a time.

The model picks one next token from those chances, writes it onto the end, and runs again. It can only see a limited stretch of text at once. That stretch is the context.

I satstart byguess 1 theguess 2 riverguess 3

Nothing in that loop checks whether “river” is true in the world. It only checks what the chances say.

Learning scores each guess.

So far we watched a finished model answer. Learning is how those numbers got good. Take a real sentence and cover the next token. The model gives that token a chance. The loss is the score for that guess: small when the chance was high, large when the model barely considered the token that was actually there.

loss = −log(chance of the real next token)

20% chance · loss 1.61

At 100% the loss is 0. The model was not surprised. At 1% the loss is about 4.6. It was very surprised. Language is unsure, so a trained model does not sit at 0.

Training is a small step downhill, repeated.

The weights start as random numbers. The loss is one number. The model is billions of numbers. To make the loss smaller, each number has to move a little. Backpropagation walks the loss and computes the slope for every weight. That slope is the gradient. It says which way. One example nudges every number. The next example nudges them again. This long first pass is pre-training. A frontier run uses thousands of GPUs for weeks or months. The count labs publish is tokens, often in the trillions, not a neat pile of separate documents.

new number = old number − step size × slope

The trained model is the numbers you keep.

The articles and code were the practice text. They are not the model. The model is the weights: the inner numbers after all those steps. Copy that file and you have copied the model. When the file is published for anyone to run, it is called an open model. Nobody writes a separate rule for Python, physics, or French. Those patterns were in the practice text, and next-token training stored them in the weights.

Pre-training finishes an autocomplete.

A pre-trained model is good at continuing text. It does not yet behave like a helpful assistant. Post-training is the later passes. Instruction tuning shows it questions paired with the reply a person wanted. A preference pass shows two replies and keeps the better one, judged by a person or by an automatic check. When the check can be marked, the math matches or the tests pass, that reward is verifiable. The downhill step is the same. The score it chases is different.

Vaswani et al., 2017, the transformer. Ouyang et al., 2022, the assistant pass. DeepSeek-R1, rewards a checker can mark.

It can sound sure and still be wrong.

The loop only asks, “what token usually comes next?” If a false sentence is a likely sentence, the model will say it. Giving it tools, or fresh notes, is a later fix. The bare model does not go and check.

To answer, those numbers have to sit in memory.

The weights are large. While the model runs, they sit in fast memory, usually on a GPU. A smaller open model can fit on one card. A frontier-size model is split across many cards. Quantization stores each weight in fewer bits so the file takes less room. A busy service batches many requests on those same cards, so one chip works on several replies together. Calling an API means the numbers sit on someone else’s cards.

The next tab is the machine that holds these numbers: a graphics card, its memory, and a room full of them.

The machine

How the hardware runs a model

An LLM is a file of numbers, and a reply is a long run of multiplications. The computer that does this well is a graphics card, a GPU. A normal processor, the CPU, is the wrong shape for that job.

One careful worker, or a crowd doing the same sum.

A CPU is built for one job at a time: open a file, branch, decide. A GPU is built for the same small sum, repeated millions of times. Turning a token into the next token is that kind of sum. The weights are grids of numbers. The card multiplies those grids.

One GPU is one board.

When people count GPUs, they count boards. One board has one calculator chip, and several smaller memory chips beside it. Those memory chips, added together, are the VRAM. A 4090 is one chip plus twelve memory chips of 2 GB each, which is 24 GB. That whole board is one GPU. The chip on that board uses only the memory on that board.

How much memory the file needs.

Each weight is a number. At the usual half-precision, one weight is 2 bytes. A billion weights is about 2 GB. That is the file size before the conversation itself, which also uses a little more memory as the reply grows.

memory in GB ≈ billions of weights × 2

7 billion weights · 14 GB

A single strong gaming card has about 24 GB. This file fits on one card.

One new token re-reads the whole file.

Writing the next token does surprisingly little new arithmetic. The card reads the weights, multiplies once, and writes one token. Then it reads the weights again for the token after that. So the speed of a single reply follows how fast the memory can be read, not the headline maths speed of the chip.

seconds per token ≈ size of the file / memory read speed

A data-centre card and a gaming card can have similar maths speed and very different memory speed. The one with faster memory finishes a token sooner.

A data centre is many cards, plus power and cold air.

When the file is larger than one GPU, the model is split across several boards. Four GPUs means four chips and four separate pools of memory. The chip on one board cannot use the memory on the next board. Those boards need a fast cable between them, a rack, a large power supply, and cooling. That room is a data centre.

The next tab is who owns that machine, and who can see the text you type into it.

Two questions

Open source and frontier

These words answer different questions. Frontier asks how good the model is. Open asks whether you can hold the file. A model can be either, both, or neither.

Frontier means near the front.

A frontier model is one of the most capable models you can use right now. It handles the hardest writing and reasoning. The usual way to reach one is an API: you send text, the lab’s computers answer, and you never get the weights. That is a closed frontier model. The word frontier does not mean secret. It only means the model is at the front of what current models can do.

Open weights means the file is published.

An open-weight model is a weight file you can download and run. A GPU you rent or own does the multiplications. The lab usually keeps the training text and the full recipe, so you can run the model without being able to rebuild it from nothing. People often call this open source. The tighter name is open weights.

open source = weights + training code + the data to rebuild it

If any of those three is missing, you have a published model, not a model you could reproduce.

The two lines cross.

A smaller open file can fit on one GPU and still sit well behind the frontier. A huge open file can sit near the frontier and still need a row of GPUs in a data centre. A closed API can be the frontier, and a closed API can also be a smaller, cheaper model. Quality and ownership are separate.

What you give up on each side.

Closed frontier

The strongest answers, and no GPU to run. The prompt goes to the lab. They can store it, change the model, or close the account.

Open weights

You can hold the file. On your own GPU the prompt stays with you. A small file fits one board. A file near the frontier needs many boards.

Open source

Rare. You would get the weights and enough code and data to train that model again. Running a copy does not require that.

What makes one model better.

A better model is one whose weights guess a more useful next token on the job you have. Useful means the reply is right, it does what you asked, and it can keep going without falling apart. Open or closed does not decide that. Three things do.

What it practiced on

The practice text is not stored. The habits are, in the weights. A model that practiced on careful code is better at code. A model that practiced on junk gets good at junk.

A second pass

The first training only teaches what usually comes next. Instruction tuning is a later pass on examples of a reply a person wanted. That is why one model answers you, and another just continues the sentence.

How many weights

More weights can hold more patterns. A huge file that was not trained for long enough can lose to a smaller file that was. Extra size also needs more GPUs.

Better is a job, not a single trophy. The frontier model is the one that wins the hardest jobs today. A smaller open file can still be the one you want when the job is ordinary and the prompt has to stay on your machine.

The next tab is what changes when you run that file yourself.

On your machine

What self-hosting is

Self-hosting means you download an open-weight file and a program on a computer you control does the multiplications. The prompt stays on that computer. You get tokens back from it, not from the lab that trained the model.

Where the prompt goes.

The same open file can sit in three places. Only the last one keeps the prompt on hardware you own, with no account for a lab to close.

Their API

You send the prompt to a company. They hold the weights. They can store the text, change the model, or close the account. This is true even when the model they serve is an open file.

A rented GPU

You load the file and run it. The prompt is on their machine. They can see that machine, and they can switch it off.

A GPU you own

The file and the prompt stay on your computer. No other company has to see the text or keep the model running.

Three things have to be on the machine.

The weight file, a runner, and enough VRAM. The runner is the program that loads the weights and writes the next token. Your own software talks to the runner on that same machine, the way it would talk to an API, except the address is yours.

The file, the conversation, and a little spare.

The hardware tab sizes the weight file alone: about 2 GB for each billion weights at half precision. A real run needs more than the file. While it answers, the runner keeps a note of the prompt and of the tokens already written, so the model can look back. That note is the KV cache. It grows when the conversation gets longer, and it grows again when several conversations run at once. The weights stay the same size. Leave a little VRAM free for the runner itself.

VRAM ≈ weight file + KV cache + a little spare

Fewer bits, so a larger file can fit.

Quantization stores each weight with fewer bits. At half precision a weight is 2 bytes. At 4 bits it is about half a byte, so the file shrinks to about a quarter. A model that needed several boards can then fit on fewer of them. The answers get a little less exact. You traded some accuracy for room. You did not make a frontier model out of a smaller one.

4-bit memory in GB ≈ billions of weights × 0.5

Add the KV cache and the spare on top of that. A short chat on one card is the case this number is for.

What you keep, and what you still do not have.

No account to close

The lab can stop publishing new files. The copy already on your disk keeps answering. You choose when to download a newer one.

The prompt stays

On a machine you own, the text is multiplied there. A rented machine still belongs to the company that can see it.

A license, and a quality limit

The file comes with rules about who may run it. You still do not get the training text. A file that fits on one card is often behind the frontier.

One desktop card needs a normal plug and a fan. A file near the frontier needs a row of cards, a large power supply, and a room that can take the heat. That room is the data centre from the hardware tab. Self-hosting changes who holds the numbers. It does not change how much electricity a large file uses, or how good a small file is.

A first run is a check, on practice text.

Pick an open file that fits on one board, including the conversation note. Load it with a runner. Send practice text that is not private, and read the answers. You are checking whether this file is good enough for the work. Private text belongs on a machine you control, after that check. A file that fails the check does not become worth a bigger machine.

You can keep training it on your own examples.

Answering leaves the weights as they are. Training moves them. If you hold the file, you can show it a pile of your own text and run the same downhill step again. That later pass is fine-tuning. You start from a model that already knows language. You are teaching it a habit: the tone, the shape of the answer, the job. The new file is yours.

Write many examples of the reply you want. The loss scores each guess. The gradient nudges the numbers. After enough examples, the model tends to answer in that way on its own.

The habit

Fine-tuning is for how it acts. A long pile of your writing teaches it to sound like that pile, and to follow the kind of reply you showed it.

The page

A particular fact belongs in the prompt. Put the page there, or fetch the relevant pages first. The weights hold the habit. The prompt holds the page in front of it.

The memory

Rewriting every weight needs much more VRAM than answering, because the card must also keep the slope for each number. LoRA freezes the original file and trains a small set of extra numbers. That often fits on the same card that can already run the file.

The examples stay on the machine that does the training. On a GPU you own, that machine is yours. On a rental, the host can see the examples too. The license has to allow this further training. A closed API can sometimes train a copy for you, and the lab keeps that file.

Frontier API

Privacy 3/10

The book still leaves your machine.

The prompt leaves your machine. It goes to OpenRouter, then to Bedrock or Vertex, where Claude Opus 5 holds the weights. The packet is kept short on purpose: a mandate, a few instruments, a short view, a few public prices, and, on the second pass, the titles of the checks. The full private write-ups of those checks are not what the code sends. What does leave is enough to reconstruct the book: the stance, the sizes, and the fact that this PM asked.

OpenRouter’s own docs say a request with zero data retention is routed only to endpoints that do not store the prompt, and that OpenRouter itself does not keep prompts unless logging is turned on. data_collection: deny is how the code also refuses providers that may store data or train on it. Bedrock’s docs say a retention mode of “none” means AWS does not write the request to durable storage and does not share it with the model provider. Anthropic’s Bedrock terms say Anthropic may not train on that customer content, and that the usage data Anthropic receives excludes the content.

That is a stack of promises, not a single lock. OpenRouter still sees the prompt in transit. AWS or Google still runs the machine. If a safety system flags the call, Anthropic’s direct API policy keeps flagged inputs and outputs for up to two years, and even a zero-data-retention deal allows that. Bedrock’s newer “covered” models can require a 30-day review inside AWS. AWS says Claude models released before Claude Fable 5 do not have that new requirement. Opus 5 is the model in the code. Confirm on the AWS account that this model is actually allowed at retention mode “none”, because a model that requires retention will be blocked, or kept, depending on the setting.

Seen in the Skillify files: the OpenRouter flags are zdr: true, data_collection: 'deny', allow_fallbacks: false, and only: ['amazon-bedrock', 'google-vertex']. The Grok retry is only: ['xai']. Sources: OpenRouter ZDR, AWS Bedrock retention, Anthropic on Bedrock, Anthropic commercial retention.

Who can stop it 2/10

Anthropic can suspend the key, and an outage stops the reply.

Anthropic’s usage policy says that if they suspect a violation they may warn, throttle, limit, suspend, or terminate access. Finance is a high-risk use when the product makes a personalized recommendation to buy, sell, hold, or allocate among specific investments. The rule is a qualified person, with the authority to change the output, must review it before it is delivered as advice or used to implement a decision, and the person affected must be told AI was used. A book that a portfolio manager reads and then decides on fits that review. A book that is sent straight through to an order does not. They can cut the key off for that, or for a mistake in how they read the traffic. An outage cuts it off with no policy judgment at all.

The same call can also die because OpenRouter, AWS, or Google is down, or because the account is unpaid. On the listed errors the code does not stop. It retries the prompt on Grok 4.6 at xAI. That keeps a reply coming, and it means xAI can see the book on the days Opus fails. xAI can apply their own terms to that retry. None of these companies has to keep serving Skillify.

Seen in the Skillify files: fallback statuses include 401, 403, 408, 429, and 5xx, then Grok 4.6. Sources: Anthropic Usage Policy PDF, Anthropic’s 2026 policy note.

Quality 8/10

This is the strongest model of the three, and it is untested on your packets.

This is the frontier end of the models tab. The weights stay at the lab. You are renting the guesses. On Artificial Analysis’s Intelligence Index, read on 9 October 2026, Claude Opus 5.5 at maximum effort scores 58, the highest on that board. The same model at high effort, which is the effort Skillify sets, scores 54. The best open-weight models on that same index are MiMo-V2.6-Pro at 46, GLM-5.3 at maximum at 45, and Kimi K3 at maximum at 44. Opus 5.5’s list price is $4 per million input tokens and $20 per million output tokens. Opus 5, the model named in the code, is listed at $5 and $25. I did not find an Intelligence Index row for Opus 5 itself on the page I read. Anthropic’s own write-up says Opus 5.5 leads Opus 5 by 11 points on one coding benchmark, Terminal-Bench 4.0.

Those scores are general tests: agents, code, science, professional writing. They are not Skillify packets. A model can win the index and still miss a mandate, a size, or a flat sleeve. The useful fact is the gap: the open files nearest the front are still several points behind the frontier model Skillify is paying for, and the small file that fits on one GPU is further behind again. DeepSeek V4.1 Flash at maximum scores 39 on the same index.

Fine-tuning does not run on this path. The weights are not yours. You cannot nudge them. Instruction tuning already happened at the lab. What you can change is the packet: the checks you invite, the examples in the prompt, the schema. That changes the habit for one call. It does not change the file.

Sources: Artificial Analysis leaderboard, Opus 5.5 write-up, Anthropic pricing.

Speed 4/10

Two thinking passes, and a public high-effort reply took about 45 seconds.

The wait is two passes, one after the other, with thinking turned on. Artificial Analysis measured Opus 5.5 at high effort at 75 tokens a second, about 38 seconds to the first chunk, and about 45 seconds for the whole reply, on their task. At maximum effort the same model took about 725 seconds before the first chunk. Skillify sets effort to high, on Opus 5, twice. I did not find a measured latency for a Skillify packet. A shorter packet should start sooner than a giant benchmark. Two passes means the PM waits for the first reply, then waits again. The hardware fact still holds: each new token re-reads the weights, and a long think is a long row of tokens.

Cost 8/10

A full pair of replies caps near $0.82, and idle time is free.

Setup, and who else is in the room 9/10

This path is already how the live call works.

This path is already how the live call is built. Experiments

The question is which setup Skillify should trust: the frontier API it uses now, an open file on a rented GPU, or that same open file on a GPU you own. No run has been started. The fake Skillify packets are not written yet. The public tests below can be downloaded before those packets exist.

How a run is done.

Freeze the prompt list before any model sees it. Send that same list to each setup. Record the reply, the seconds from send to finished text, and the dollars. Score without knowing which setup wrote the answer. Then write the numbers here. Do not edit the prompts after the first score.

Frontier needs no new machine. The live Skillify path already calls Claude Opus 5. Rented means a card you hire for the hours of the run. Owned means a card you buy later and load with the file the rental already produced. Do not buy a card for round one. A rental can train the weights. It cannot copy the privacy of a machine you own.

Seen in the Skillify files: the live call is OpenRouter to a zero-retention Bedrock or Vertex endpoint, model anthropic.claude-opus-5, thinking effort high, two passes, 16,384 token cap each.

The variables.

Independent variable

The setup: frontier API, rented open file, or owned open file. A second change, only on the open file, is base weights versus a LoRA trained on your examples.

Dependent variables

Rubric score out of 10, pass@1 on a test that checks itself, seconds to finish, and dollars for that run.

Constants

The same prompts, in the same order. The scorer is blind. Nothing is trained on the test prompts. Temperature and effort are written down and kept. The fake packets, once written, stay frozen.

The frontier cell changes two things at once: the weights and the host. Rent versus owned can use the same file, so that pair isolates the machine. A score gap between frontier and rented is a gap between files, not a gap between landlords.

Scoring rubric.

Each item is 0, 1, or 2. The ten points are the sum. A public test that already has a checker keeps that checker’s pass or fail, and we still time it and cost it. This rubric is for the Skillify book, and for any answer a person has to judge.

Schema

2: the reply is the JSON the desk can read. 1: the fields are there and broken. 0: prose, or a refusal to answer in the shape we asked.

Mandate

2: it stays inside the instruments and the rules in the packet. 1: one sleeve wanders. 0: it invents a market the packet did not allow.

Decision

2: a direction and a size, or an explicit flat. 1: a direction with no size. 0: no action a person could check.

Grounding

2: the reasons use numbers that were in the packet. 1: mixed with figures it made up. 0: the prices are invented.

Use

2: a portfolio manager could act, or could correctly do nothing. 1: they would have to rewrite it. 0: they would ignore it.

Two people can score the same blind pile. If they differ by more than 2 points, a third read breaks the tie. This is the small version of a blind ranking. Chatbot Arena does that with a crowd. We do it with the desk. Chatbot Arena.

The tests.

Public rankings do not use one exam. Artificial Analysis builds an index from ten evaluations, weighted agents 30, coding 20, general 30, science 20. About 45 percent of that weight is a private test we cannot rerun. We run the public ones. We do not invent an index number of our own. Where they have already published a score for Opus 5.5, that number stays a citation, not our result.
